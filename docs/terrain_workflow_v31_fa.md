# راهنمای عملیاتی DEM و مشتقات توپوگرافی — نسخه ۳.۱

> **وضعیت علمی:** این workflow فقط ویژگی‌های توپوگرافی را از ASTER GDEM V003 تولید می‌کند. خروجی‌ها امتیاز مدل منگنز را تغییر نمی‌دهند و هیچ ادعایی دربارهٔ احتمال، ذخیره، عیار، مرز معدن یا وضعیت حقوقی ایجاد نمی‌کنند.

## هدف و دامنه

این نسخه، ۹ تایل ASTER GDEM V003 موجود در ریپو را پیش از پردازش با SHA-256 کنترل می‌کند، برای ناحیهٔ تحلیل، داده را در CRS متریک مناسب نی‌ریز بازنمونه‌برداری می‌کند و لایه‌های زیر را می‌سازد:

| لایه | فایل | واحد / تعریف |
|---|---|---|
| ارتفاع | `dem_elevation_m.tif` | متر |
| شیب | `slope_degrees.tif` | درجه |
| جهت شیب | `aspect_degrees.tif` | درجه در جهت ساعت‌گرد از شمال؛ سطح تخت `NoData` است |
| انحنای طولی | `profile_curvature_per_m.tif` | `1/m` |
| ناهمواری | `roughness_stddev_m_3x3.tif` | انحراف معیار ارتفاع در پنجرهٔ ۳×۳، متر |
| سایه‌روشن | `hillshade_315az_45alt.tif` | ۰ تا ۲۵۵، آزیموت ۳۱۵° و ارتفاع خورشید ۴۵° |

تمام رسترها تک‌باند، `float32`، در `EPSG:32640`، با تفکیک ۳۰ متر و مقدار `NoData=-9999` هستند. پردازش در CRS متریک انجام می‌شود تا مشتقات شیب و انحنا از مختصات جغرافیایی محاسبه نشوند.

## ورودی‌های کنترل‌شده

- تایل‌ها: `data/remote_sensing/aster_gdem_v003/*.tif`
- manifest کنترل صحت: `data/acquired/aster_gdem_v003_sha256.txt`
- منشأ رسمی ASTER و محدودیت آن: `data/remote_sensing/aster_gdem_v003/metadata.json`
- لایه‌های شواهد پروژه برای ساخت AOI موقت: واحدهای میزبان، گسل‌های تقریبی و رخداد منگنز تأییدشده

هر تایل درج‌شده در manifest باید وجود داشته باشد و SHA-256 آن دقیقاً با manifest یکسان باشد؛ در غیر این صورت اجرای production متوقف می‌شود.

## AOI و مرز تحلیل

اگر `--aoi-file` داده نشود، اسکریپت از لایه‌های فعلی پروژه یک **پوشش مستطیلی موقتِ شواهد** می‌سازد و ۱۰۰۰ متر buffer اعمال می‌کند. این مرز صرفاً پنجرهٔ پردازش است، **مرز محدوده، کاداستر یا مجوز نیست**.

برای تحلیل محدودهٔ واقعی، یک فایل برداری CRSدار ارائه کنید:

```bash
.venv/bin/python scripts/build_terrain_derivatives.py \
  --aoi-file data/incoming/approved_aoi.geojson
```

فایل AOI باید حداقل یک هندسهٔ معتبر و CRS صریح داشته باشد. دادهٔ محلیِ دریافت‌شده در `data/incoming/` عمداً در Git نادیده گرفته می‌شود؛ فقط داده‌ای را که مجوز اشتراک و ثبت provenance دارد به مسیر نسخه‌بندی‌شده منتقل کنید.

## اجرای استاندارد

### ۱. نصب محیط

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt -r requirements-geospatial.txt
```

### ۲. اجرای کامل و بازتولیدپذیر

```bash
make ci PYTHON=.venv/bin/python
```

یا فقط مشتقات DEM:

```bash
make terrain PYTHON=.venv/bin/python
```

فرمان کامل، مدل غربالگری موجود را بازتولید می‌کند، نقشه‌ها و مشتقات DEM را می‌سازد و همهٔ اعتبارسنجی‌ها را اجرا می‌کند. برای جلوگیری از تغییر ناخواستهٔ امتیازها، workflow DEM هیچ وزن جدیدی به مدل اضافه نمی‌کند.

## کنترل کیفیت و جلوگیری از ادعاهای غیرمجاز

`validate_terrain_outputs.py` این موارد را بررسی می‌کند:

1. کنترل SHA-256 تمام تایل‌های ASTER موجود در manifest؛
2. وجود و checksum همهٔ شش خروجی؛
3. CRS، اندازهٔ پیکسل، نوع داده، `NoData` و ابعاد سازگار رسترها؛
4. وجود دادهٔ معتبر در هر لایه؛
5. تطابق ۱۰ هدف موجود با جدول terrain؛
6. باقی‌ماندن ویژگی‌ها در وضعیت `NOT_APPLIED`؛
7. عدم تغییر وضعیت حقوقی یا ادعای دقت مدل.

## ورود DEM به مدل؛ شرط لازم، نه اقدام خودکار

DEM می‌تواند برای استخراج ویژگی یا طراحی بازدید میدانی مفید باشد، اما برای وارد شدن به مدل باید یک تصمیم مدل‌سازی مستند شود و پیش از انتشار همهٔ شرایط زیر برقرار باشد:

- AOI تأییدشده و لایهٔ زمین‌شناسی/GIS با provenance معتبر؛
- دادهٔ ژئوشیمی مکانی‌دار با QA/QC؛
- برچسب‌های مستقل مکانی و جداسازی آموزش/آزمون؛
- تعریف ویژگی، جهت اثر، روش نرمال‌سازی و کنترل multicollinearity؛
- آزمون ablation که بهبود `precision@k`، recall و PR-AUC را روی آزمون مستقل نشان دهد؛
- بازهٔ اطمینان و بازبینی زمین‌شناس مسئول؛
- اجرای موفق `scripts/validate_evidence_gates.py` و مستندسازی تغییر نسخهٔ مدل.

تا پیش از این دروازه‌ها، تغییر خودکار وزن‌ها یا رتبه‌بندی با DEM غیرمجاز است.

| داده | محل پیشنهادی | حداقل metadata |
